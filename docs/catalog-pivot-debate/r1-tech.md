## 0. 한 줄 결론

**엔진은 이미 컨셉과 떨어져 있다.** LH 는 EB 코어를 **한 줄도 안 바꾸고**(neon-drift.js 동일) 렌더러를 **서브클래스 한 파일**로 갈아 끼웠다. 같은 구조를 EB 에 넣으면 그래픽 · 컨셉 교체는 **기술 쪽 2~3일**이고, 일정을 정하는 건 그림(AD)과 셸 문구 · 흐름 정리다. 그래서 방향은 기술이 아니라 **아트 · 디자인이 정한다** — 기술은 어느 쪽이든 받을 수 있게 먼저 판을 깐다.

**새 숫자가 우선순위를 바꿨다:** LH(추정)는 로딩 0.2초 · 코드 아트인데도 **게임이 뜬 168세션 중 60%가 30초 안에 떠났다.** 즉 "그림 방식 · 로딩 속도"만으로는 첫 30초가 안 막힌다. 기술이 할 일 1순위는 **EB 첫 30초 경로의 기술적 마찰 제거 + 그 30초에 무슨 일이 있었는지 재는 계측**이고, 그래픽 교체는 2순위다.

## 3. 코드 아트 vs 기존 이미지 큐레이션 (기술 비교)

| 항목 | 기존 webp 큐레이션 | 코드 아트(LH 방식) |
|---|---|---|
| 용량 | 테마 2.3MB(zip 2.2MB). 큐레이션 · 리사이즈로 줄여도 해상도와 반비례 | 아트 JS ~150KB급(LH 4테마 기준). EB 3시대 × 11단계면 비슷하거나 약간 큼 |
| 로딩 | 이미지 요청 ~80개(지연 로드), 첫 보드에 보드 배경 768px · 타일 11장 필요. 지금 로딩 418ms(Playgama 측정) | 요청 0. 첫 그리기 조합당 0.2~0.3ms(지연 생성) · 배경은 리사이즈 때 오프스크린 1회 |
| 실패 모드 | 경로 · zip 구분자 · 지연 로드 → **숫자 타일** | 함수 예외 → 그 함수만 placeholder. 네트워크 실패 없음 |
| 선명도 | 고정 해상도. 큰 폰 · 태블릿 · 데스크톱 전체화면에서 배경 흐림 | 기기 px 로 그려 **모든 크기 선명**. 단 캐시는 DPR 상한(2~3) 필요 |
| 프레임 비용 | drawImage 1회/타일 — 가장 쌈 | 캐시 후 동일(drawImage 1회). 캐시 미스 · 애니 배경은 더 비쌈 → 저가폰 미측정 |
| 메모리 | 디코드된 이미지 전부(배경 512² × 33 등) | 오프스크린 캔버스(조합 수 × px²). 4px 단위 반올림 + 상한(LH 200개에서 비움) 필요 |
| 제작 비용 | 0~낮음(있는 그림) — **단, "새 AI 이미지 금지"라 바꿀 여지도 거의 없음** | 높음: 캐릭터 1개 15~30분, 배경 · 장면 별도. **기술 비용은 어댑터 1회로 끝**, 나머지는 AD |
| 반려 사유 대응 | 출처 그대로 | 출처가 손으로 쓴 코드 → "큐레이션된 아트 디렉션" 주장 가능(판정은 AD · PD) |

**기술 판단:** 섞어 쓸 수 있다. 어댑터는 "코드 아트 함수가 있으면 그것, 없으면 기존 이미지, 그것도 없으면 placeholder" 3단으로 짠다 → 시대 하나씩 바꿔 넣어도 빌드가 늘 완결된다.

## 7. 방향 투표 — **C (그래픽 제작 방식 교체 + 범위 압축, 같은 앱 id)**, B 로 갈 수 있게 판을 깐다

- 이유 1: 반려 사유 두 개 중 **"100% 생성형 AI"는 그림 출처 문제**고, 기술적으로 가장 싸게 바꿀 수 있는 축이다(어댑터 2일 + AD).
- 이유 2: 코어 · 지층 sim · 저장 · LB 를 건드리지 않아 위험이 그림 · 첫 30초 셸에만 있다. B 는 컨셉 · 문구 · 흐름이 같이 바뀌어 무엇이 지표를 움직였는지 갈라 볼 수 없다(EB 는 3 played 라 비교 기준선도 없다 — 바꾸는 손잡이 수를 줄이는 게 더 중요).
- 이유 3: 어댑터는 B 의 선행 작업과 **똑같다**. C 로 만들고 2라운드에서 컨셉 교체가 정해지면 같은 판 위에 그림 · 문구만 더 얹는다.
- 다만 **"신선한 플레이 경험 없음"은 C 로 안 풀린다** — 이건 게임 디자인 · AD 쪽 제안(변형 메커닉 · 장면 연출)에 기댄다. 그쪽에서 B 가 설득력 있으면 기술은 반대하지 않는다(비용 차이 2~3일).
